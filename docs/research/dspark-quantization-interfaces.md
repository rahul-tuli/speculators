# DSpark quantization and offline calibration interfaces

This is an interface investigation for the requested `RedHatAI/Qwen3.8-27B-speculator.dspark` examples. It does not reproduce or evaluate the user's internal recovery results, run a quantization, or prove a deployable output. Source code references below are pinned to the checkouts inspected on 2026-11-12.

## Target and model inputs

The [target model card](https://huggingface.co/RedHatAI/Qwen3.8-27B-speculator.dspark) describes a five-layer DSpark drafter using `Qwen/Qwen3.8-27B` as verifier, auxiliary layers 4, 12, 20, 28, 36, 44, 52 and 60, a vanilla rank-256 Markov head, and an enabled confidence head with Markov features. The [checkpoint config at revision `87ca2fdc`](https://huggingface.co/RedHatAI/Qwen3.8-27B-speculator.dspark/blob/87ca2fdc67f316f6c1f9ebc7ef7bbb0ad299a4ce/config.json) records hidden size 5120, full draft vocabulary 248320, `block_size=8` and `sample_from_anchor=true`.

At speculators revision [`988ed16b`](https://github.com/rahul-tuli/speculators/tree/988ed16b1f91315942049da3093d88dba70c45d9), [`DSparkDraftModel.forward`](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/src/speculators/models/dspark/core.py#L121) expects concatenated auxiliary `hidden_states`, `input_ids`, `loss_mask`, `verifier_last_hidden_states`, and `document_ids`, optionally `position_ids`. It executes a training-oriented backbone and computes loss, rather than accepting only the tokenized text supplied to a conventional causal language-model example. The [backbone](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/src/speculators/models/dflash/core.py#L370) builds anchor blocks, calls the `fc` fusion projection and transformer layers, and computes target and draft logits. Therefore calibration needs a compatible dataset and forward path; a standard text-only example is not sufficient evidence of compatibility.

The [DSpark head definitions](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/src/speculators/models/dspark/model_definitions.py) include both an embedding and linear layers within the Markov head, plus a linear confidence projection. Targeting only `Linear` avoids embedding modules but can still target those head projections; the requested recipe must exclude the Markov and confidence heads as well as embeddings.

## Existing offline data

The [training tutorial](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/docs/user_guide/tutorials/train.md#L220) uses `speculators prepare-data`, a verifier vLLM extraction server, and `speculators generate-offline-data` to cache verifier hidden states. [`generate-offline-data`](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/src/speculators/cli/generate_offline_data.py#L391) consumes preprocessed records and a running extraction endpoint; `--validate-outputs` checks token correspondence and sequence lengths. The [launcher](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/scripts/launch_vllm.py#L461) accepts explicit target layer IDs and, by default, appends the verifier's last layer if it is not already among them. Any use of this launcher must include `--provenance-dir` under this repository's agent instructions.

[`SpeculatorsDataset`](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/src/speculators/train/data.py#L105) combines Arrow records with a hidden-state source, checks token alignment, flattens the auxiliary dimensions, and takes the final payload layer as the verifier final hidden state. Its batch path constructs document IDs. This suggests a reusable source for calibration inputs, but no direct llm-compressor integration was run or established here. Earlier [calibration-input investigation](https://github.com/rahul-tuli/speculators/issues/102#issuecomment-5760407926) identified FP8 hidden-state storage as requiring scale-aware restoration for its Qwen3-8B/DFlash cache; that cache and its validation do not establish compatibility with this Qwen3.8/DSpark model.

## llm-compressor interfaces and configuration gap

At llm-compressor revision [`eac6972c`](https://github.com/vllm-project/llm-compressor/tree/eac6972ca25f9e67abd8011aad5bb30ef9915e55), its [FP8 example](https://github.com/vllm-project/llm-compressor/blob/eac6972ca25f9e67abd8011aad5bb30ef9915e55/examples/quantization_w8a8_fp8/fp8_block_example.py) applies `QuantizationModifier` to linear layers with `scheme="FP8_BLOCK"` and calls `oneshot` without a dataset. Its [NVFP4 example](https://github.com/vllm-project/llm-compressor/blob/eac6972ca25f9e67abd8011aad5bb30ef9915e55/examples/quantization_w4a4_fp4/qwen3_5_9b_gptq_imatrix_example.py) combines `GPTQModifier`, `scheme="NVFP4"`, and `weight_observer="imatrix_mse"` in one recipe, with calibration data. Both examples target ordinary transformer model classes, not DSpark.

The [`oneshot` API](https://github.com/vllm-project/llm-compressor/blob/eac6972ca25f9e67abd8011aad5bb30ef9915e55/src/llmcompressor/entrypoints/oneshot.py#L409) accepts a model and either a Hugging Face dataset or a prebuilt PyTorch `DataLoader`; the [loader](https://github.com/vllm-project/llm-compressor/blob/eac6972ca25f9e67abd8011aad5bb30ef9915e55/src/llmcompressor/datasets/utils.py#L125) passes a supplied `DataLoader` through without text tokenization. This is a potential integration seam, not a demonstrated working DSpark calibration. Calibration invokes model inputs as keyword arguments through its [whole-model subgraph](https://github.com/vllm-project/llm-compressor/blob/eac6972ca25f9e67abd8011aad5bb30ef9915e55/src/llmcompressor/pipelines/sequential/helpers.py#L149); the default data-dependent pipeline and the DSpark training forward, tracing behavior, memory use, and loss/head handling require an actual integration check. The [calibration context](https://github.com/vllm-project/llm-compressor/blob/eac6972ca25f9e67abd8011aad5bb30ef9915e55/src/llmcompressor/utils/helpers.py#L136) can replace an identified output head with a meta-device forward, which needs particular care if the chosen DSpark forward consumes its logits.

There is a concrete config-compatibility concern before calibration. The checkpoint config has `speculators_model_type` but no top-level Hugging Face `model_type`; `SpeculatorModel` has its own [config/class loading path](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/src/speculators/model.py#L251). llm-compressor's [`oneshot.validate_model`](https://github.com/vllm-project/llm-compressor/blob/eac6972ca25f9e67abd8011aad5bb30ef9915e55/src/llmcompressor/entrypoints/oneshot.py#L340) calls `AutoConfig.from_pretrained(model.config.name_or_path)`. In a config-only probe in the speculators environment, `AutoConfig.from_pretrained` on the pinned target revision failed with `ValueError` requiring `model_type`; `SpeculatorModelConfig.from_pretrained` on that same revision returned `DSparkSpeculatorConfig`. This establishes a risk in the generic validation route, not a tested full `oneshot` failure or a proven workaround.

[`SpeculatorModel.from_pretrained`](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/src/speculators/model.py#L394) reloads verifier-owned weights; the [DFlash save rules](https://github.com/rahul-tuli/speculators/blob/988ed16b1f91315942049da3093d88dba70c45d9/src/speculators/models/dflash/core.py#L39) exclude verifier weights and, for full-vocabulary drafts, the verifier-derived embedding and LM head. llm-compressor [wraps `save_pretrained`](https://github.com/vllm-project/llm-compressor/blob/eac6972ca25f9e67abd8011aad5bb30ef9915e55/src/llmcompressor/entrypoints/utils.py#L91) and can save compressed weights. The interaction of this save path, speculator-specific config, omitted weights, and vLLM loading must be checked end to end; no saved quantized checkpoint was produced in this investigation.

The pinned [compressed-tensors presets](https://github.com/vllm-project/compressed-tensors/blob/70e7167581860af0807546879e3cd0357085e246/src/compressed_tensors/quantization/quant_scheme.py#L427) define FP8_DYNAMIC with channel-wise weights and dynamic per-token activations, and FP8_BLOCK with 128×128 weight blocks and dynamic 128-element activation groups. The [NVFP4 preset](https://github.com/vllm-project/compressed-tensors/blob/70e7167581860af0807546879e3cd0357085e246/src/compressed_tensors/quantization/quant_scheme.py#L184) uses 4-bit grouped weights and activations with group size 16. The user requested `FP8_DYNAMIC` as the example default, an explicit one-line switch to `FP8_BLOCK`, and combined NVFP4 GPTQ+iMatrix as a separate example.

## Environment and limits

The speculators virtual environment reported speculators `0.10.0a64`, Transformers `5.20.2`, compressed-tensors `0.17.0`, Torch `2.14.0+cu130`, and hs-connectors `0.9.1a64`; llm-compressor was not installed there. The llm-compressor virtual environment reported llm-compressor `0.15.1.dev47+geac6972ca`, Transformers `5.20.2`, compressed-tensors `0.17.0`, and Torch `2.14.0+cu130`; speculators was not installed there. These are observed local versions, not a verified supported combined installation or minimum-version guarantee. No GPU workload, compressed checkpoint, vLLM deployment, or quality-recovery experiment was run. Validate a compatible joint environment, data adapter, forward path, serialization and serving before treating the examples as runnable.
