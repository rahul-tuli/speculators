# Drafter quantization: hardware and kernel gate

Research for [Determine which hardware and kernels support defensible quantization measurements](https://github.com/rahul-tuli/speculators/issues/103), resumed 2026-09-21. Scope: existing Gaussian versus real calibration, acceptance first, then latency and throughput. No model servers, full benchmarks, installs, or checkpoint changes were run. The resumed investigation inspected four existing DFlash exports and ran bounded GPU linear operations; it did not validate complete model loading or acceptance.

## Decision

Use H100 for BF16/FP8 acceptance and subsequent native FP8 speed measurements after checkpoint smoke checks. **Do not accept H100's observed automatic NVFP4 dispatch as a W4A4 calibration experiment:** the installed vLLM selects Marlin W4A16, which omits activation quantization. Explicit NVFP4 emulation is a candidate acceptance-only path, subject to model-level numerical and loading validation. Reserve native NVFP4 speed comparisons for a compatible Blackwell device and compiled kernel; rerun all speed reference arms on that same device. Dispatch also depends on environment overrides: `VLLM_BATCH_INVARIANT=1` selected emulation on this H100.

## Concrete support result

The [runnable probe](drafter-quant-hardware/probe.py) imported kernel classes and called `is_supported()` plus `init_nvfp4_linear_kernel()` without allocating a model:

| Probe                                           | Result on H100                         |
| ----------------------------------------------- | -------------------------------------- |
| `CutlassNvFp4LinearKernel.is_supported()`       | false: CUTLASS FP4 kernels unavailable |
| `MarlinNvFp4LinearKernel.is_supported()`        | true                                   |
| `EmulationNvFp4LinearKernel.is_supported()`     | true                                   |
| `CutlassFP8ScaledMMLinearKernel.is_supported()` | true                                   |
| Default `init_nvfp4_linear_kernel()`            | `MarlinNvFp4LinearKernel`              |

At vLLM revision above, [`kernels/linear/__init__.py`](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/kernels/linear/__init__.py) puts Marlin before emulation, including when `use_a16=False`. [`nvfp4/marlin.py`](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/kernels/linear/nvfp4/marlin.py) calls a weight-only GEMM and does not use the calibrated activation global scale. Thus automatic fallback changes the experiment's numerical treatment, not just its speed.

[`nvfp4/emulation.py`](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/kernels/linear/nvfp4/emulation.py) and [`nvfp4_emulation_utils.py:456`](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/layers/quantization/utils/nvfp4_emulation_utils.py#L456) instead quantize/dequantize activations with their global scale, dequantize packed weights, and multiply in the input dtype. The registry supports `--linear-backend emulation`; verify selected kernels in the eventual launch because this is a serving-wide backend option and unsupported layer types can warn/fall back. `VLLM_BATCH_INVARIANT` overrides backend choice, using supported CUTLASS or else emulation. Source inspection and the bounded operation establish W4A4 behavior, **not** empirical equivalence to Blackwell or successful model serving. Label any resulting acceptance plots “NVFP4 W4A4 emulation, H100”; do not call its latency native NVFP4 performance.

Native CUTLASS NVFP4 requires CUDA runtime at least 12.8 and a compiled SM100/SM120 family kernel, per [`nvfp4_scaled_mm_entry.cu:71`](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/csrc/libtorch_stable/quantization/fp4/nvfp4_scaled_mm_entry.cu#L71). Blackwell access is not present in the observed two-device environment. NVIDIA's [NVFP4 architecture description](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/) confirms native microscaled FP4 support on Blackwell. FP8 H100 hardware acceleration is documented in [the revision-pinned vLLM FP8 guide](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/docs/features/quantization/llm_compressor/fp8.md). Device branding alone is not sufficient: inspect the chosen backend and compiled support on the actual Blackwell host.

## Existing checkpoint evidence

The four existing exports were created by one-sample, 512-token DFlash calibration smoke runs, not an experimental budget. [Original calibration results](drafter-quant-hardware/calibration-validation/result.md), [configs and calibration manifests](drafter-quant-hardware/calibration-validation/checkpoint-manifests), and [fresh checkpoint SHA256 values](drafter-quant-hardware/checkpoint-sha256.json) are retained; fresh hashes agree with the original recorded hashes. All four contain 36 quantized modules and positive finite scales. Observed `(N, K)` shapes are `(1024, 4096)`, `(4096, 4096)`, `(4096, 12288)`, `(4096, 20480)`, and `(12288, 4096)`. FP8 dimensions are aligned to 16; every NVFP4 packed-weight and scale shape matches `(N, K/2)` and `(N, K/16)`. This checks the stored unpartitioned shapes, not every tensor-parallel partition or full loader mapping. Source: complete [tensor inventory](drafter-quant-hardware/probe.json).

All NVFP4 fused weight global scales match across QKV and gate/up for these exports. Activation scales do not always match: random QKV layer 0 is `[350, 330, 330]`, random layer 1 `[572, 330, 330]`, and real layer 1 `[1004, 486, 486]`. Runtime selects the maximum for fused activation quantization. This is supported loader behavior, not a demonstrated load failure; it means unfused quantizer forwards and fused serving need not have identical numerics. The numerical probe below confirms that substituting the real fused maximum changes one layer's emulated output. Record the effective scales and evaluate the actual serving path rather than assuming quantizer acceptance transfers. FP8 also reduces fused input scales and requantizes fused per-tensor weight scales; differing FP8 scales are expected, not themselves an incompatibility. Sources: [NVFP4 loader](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/layers/quantization/compressed_tensors/schemes/compressed_tensors_w4a4_nvfp4.py#L96), [FP8 loader](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/layers/quantization/compressed_tensors/schemes/compressed_tensors_w8a8_fp8.py#L145), and inventory above.

## Bounded numerical check and reproduction

The probe manually assembles a single layer from each checkpoint's `layers.1.self_attn.k_proj` tensors, applies the actual NVFP4 post-load transformation and selected GEMM, and applies the selected FP8 GEMM to the corresponding FP8 tensors. The FP8 checkpoint's BF16 scale tensors are converted to FP32, matching serving's allocation/copy semantics in [`create_fp8_scale_parameter` and `create_fp8_input_scale`](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/layers/quantization/utils/fp8_utils.py#L1268). Inputs are two fixed-seed BF16 vectors of width 4096; outputs have width 1024. It avoids distributed group initialization and **does not exercise `AutoWeightsLoader`, a fused QKV module, attention, the draft proposer, or model-level acceptance**. Backend-config lookup is intercepted only for the explicit auto/emulation comparison; the real registry, capability checks, tensor transforms, and kernels run. Its initial attempt to use `create_weights` without a TP group failed in the harness ([initial log](drafter-quant-hardware/probe-initial.log)); the final probe deliberately constructs per-layer state directly.

Run from the research checkout with the captured environment:

```bash
/workspace/speculators/.venv/bin/python docs/research/drafter-quant-hardware/probe.py --output docs/research/drafter-quant-hardware/probe.json > docs/research/drafter-quant-hardware/probe.log 2>&1
```

The [raw JSON](drafter-quant-hardware/probe.json) and [log](drafter-quant-hardware/probe.log) record support, exact selected kernels, finite-output checks, and scale-perturbation deltas. These are numerical treatment checks, with no timing claims and no native-FP4 equivalence claim.

| Executed path        | Random / real arms finite         | Max absolute output delta from own to fused activation scale, random / real | Delta after multiplying own inverse activation scale by 100, random / real |
| -------------------- | --------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| FP8 CUTLASS          | Both                              | Not probed                                                                  | Not probed                                                                 |
| NVFP4 Marlin W4A16   | Both, including perturbed outputs | `0 / 0`                                                                     | `0 / 0`                                                                    |
| NVFP4 W4A4 emulation | Both, including perturbed outputs | `1.0703125 / 1.15185546875`                                                 | `9.6484375 / 9.865234375`                                                  |

The perturbation is a diagnostic sensitivity check, not an accuracy metric or a calibration recommendation. Its invariance in Marlin and nonzero response in emulation corroborate the source-level activation-treatment distinction.

## Checkpoint and shape gates before either model enters plots

1. Freeze actual revisions and patches, exported checkpoint/config hashes, and runtime kernel names. The local quantizer selects compressed-tensors `FP8` (static per-tensor W8A8) or `NVFP4` (group-16 weights and locally dynamic group-16 activations with a calibrated global scale). Sources: [revision-pinned quantization schemes](https://github.com/neuralmagic/compressed-tensors/blob/a2a210e9001d6ac45b6f294f8a66a87384c7da55/src/compressed_tensors/quantization/quant_scheme.py#L180) and [captured quantizer](drafter-quant-hardware/calibration-validation/final-source/dquant/quantize.py).
2. Validate each checkpoint's actual quantized module inventory and input/output dimensions. NVFP4's loader allocates packed weights at K/2 and scales at K/16, so require group-compatible input widths after partitioning. Native CUTLASS pads dimensions; current FP8 CUTLASS pads K/N to multiples of 16. Do not infer all checkpoint shapes from the target model name. Sources: [NVFP4 allocation](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/layers/quantization/compressed_tensors/schemes/compressed_tensors_w4a4_nvfp4.py#L38) and [FP8 padding](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/kernels/linear/scaled_mm/cutlass.py#L156).
3. Check fused QKV and gate/up global scales. NVFP4 loading takes the maximum across fused tensors and warns about differing scales; llm-compressor calls `fuse_weight_observers(model)`. The current exports' shared weight scales and differing activation scales are documented above. Sources: NVFP4 scheme file above, lines 96–138, and [llm-compressor observer fusion](https://github.com/vllm-project/llm-compressor/blob/0349b68f4a7c5b0b535596df8e8d171911c8acee/src/llmcompressor/modifiers/quantization/quantization/mixin.py#L240).
4. DFlash obtains the drafter's own quantization config and propagates it to FC, attention, and MLP projections; its loader uses `AutoWeightsLoader`. This is wiring support, not proof that either exported checkpoint loads. Sources: [revision-pinned DFlash model](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/models/qwen3_dflash.py) plus [current dirty-source patch](drafter-quant-hardware/vllm.patch), and [draft quantization config helper](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/models/utils.py#L929).
5. **DSpark heads need a separate compatibility check.** Its confidence projection is constructed in FP32 without a quantization config; its selected-row Markov path directly indexes `markov_w2.weight` and uses `baddbmm_`, bypassing the quantized linear kernel. The training-side Markov projection is an `nn.Linear`, so the experiment's default `targets="Linear"` can quantize it. An all-Linear DSpark checkpoint cannot be presumed supported merely because its backbone is supported. Either explicitly exclude unsupported heads (record the partial quantization scope consistently across arms) or implement and validate compatible serving. Sources: [DSpark serving heads](https://github.com/vllm-project/vllm/blob/98dff2a81d747d1dba01a47f939f48c3526d4206/vllm/model_executor/models/qwen3_dspark.py#L89), [DSpark training definitions](https://github.com/rahul-tuli/speculators/blob/fd69f5326d695e98434196b3860956494f4c0004/src/speculators/models/dspark/model_definitions.py#L37), and the [captured quantizer's exclusion option](drafter-quant-hardware/calibration-validation/final-source/dquant/quantize.py).

Completion gate: per-model BF16 plus both calibrated FP8/NVFP4 checkpoints must load with expected tensors/scales, produce finite outputs under the intended activation quantization, and expose comparable acceptance counters. This investigation deliberately did not run those serving checks or measure acceptance. The hardware decision is settled; checkpoint integration remains an execution prerequisite.

## Decisions and execution gates left for the map

- Decide whether the initial NVFP4 acceptance experiment is explicitly H100 W4A4 emulation, or waits for native Blackwell. H100 Marlin may be a separately labelled W4A16 arm if desired; it cannot answer the same activation-calibration question.
- Decide DSpark quantization scope: consistently exclude Markov/confidence heads in every matched arm, or plan compatible serving changes. The existing `--keep-heads-bf16` option expresses exclusion, but the serving confidence projection is FP32, so describe excluded heads as retaining their serving precision rather than assuming both are BF16.
- Before measurement, perform each selected model's complete checkpoint/forward/acceptance-counter smoke with the exact export, effective fused scales, selected kernels, and overrides recorded. Do not infer end-to-end success from the single-layer probe or one-sample calibration export.
- Native NVFP4 speed work needs actual Blackwell access, compiled native dispatch, sufficient device memory for target plus drafter, and same-device reference arms. Native-versus-emulation numerical equivalence remains untested; any equivalence claim requires a separate paired numerical check.

All launches must use `scripts/launch_vllm.py --provenance-dir <associated-run-directory>` with its appropriate subcommand/options. Preserve generated `vllm_command.txt`, `vllm.patch`, target/drafter checkpoint SHA256 files and evaluation provenance alongside eventual results. No launch provenance was generated by this research probe because no server was launched; inherited calibration-capture provenance is included solely to identify its source artifacts.
